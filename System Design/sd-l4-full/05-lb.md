# Lesson 05 — Load Balancing

**Phase:** Fundamentals  
**Session:** 5/46  
**Recommended time:** 60–90 minutes

## What you will learn

Learn why load balancers exist, L4 vs L7 behavior, routing strategies, health checks, draining, sticky sessions, and failure considerations.

This is **study documentation**. Read the explanations first; use the review section only after you have studied the lesson.

## Why load balance

Horizontal scaling creates multiple servers. A load balancer distributes requests and removes unhealthy instances from service. It improves capacity and availability, but the data layer and downstream dependencies must still scale.

## L4 vs L7

L4 balancing uses transport information such as IP/port and is protocol-agnostic. L7 understands application protocols such as HTTP and can route by path/header, terminate TLS, or enforce richer policy. Choose based on required routing intelligence.

## Algorithms

Round robin is simple; least-connections helps when request durations vary; weighted routing supports canaries or heterogeneous capacity; hashing can provide affinity but may create skew. No algorithm is universally best.

## Health checks

The balancer stops sending new work to unhealthy instances. Health checks should answer whether an instance can serve useful traffic. Overly deep checks tied to a shared dependency can accidentally remove every backend at once.

## Connection draining

During shutdown or deployment, an instance can stop accepting new work while finishing in-flight requests or long-lived connections. Draining reduces avoidable errors during rolling changes.

## Sticky sessions

Affinity sends the same client to the same backend. It can help legacy stateful apps but weakens load distribution and failover. Prefer stateless compute unless affinity is truly needed.

## Worked example — scaling a profile API

A profile API grows from one to ten stateless servers behind a load balancer. Health checks remove failed nodes; draining protects requests during deployments. If expensive image operations behave differently from normal API calls, L7 routing can direct them to a specialized pool.

## Interview lens

When adding a load balancer, say what it solves—horizontal scale, failover, routing—and whether backends are stateless.

## What to remember

Load balancers distribute traffic and participate in health/failover; they do not magically remove bottlenecks elsewhere.

## Deeper study notes

### Load balancing does not have to be one layer

A global system may have global traffic management that chooses a region, then a regional load balancer that chooses a service instance. Internal service-to-service traffic may also be balanced separately. In interviews, you can usually compress these into one or two conceptual layers unless regional routing is a focus.

### Health is not binary

A process can be alive but unable to serve useful traffic because its database pool is exhausted or it cannot load critical configuration. Conversely, if every instance fails a deep health check because one shared database is down, removing all instances gains nothing. Good health checks distinguish instance-local failure from shared dependency failure.

### Affinity can be deliberate

Sticky routing is not always bad. Stateful streaming sessions or caches may benefit from affinity. The question is whether correctness depends on it. If an instance dies, can the client reconnect elsewhere and restore state? If yes, affinity is an optimization rather than a hard dependency.

### Balancers themselves need redundancy

Managed/cloud load balancers hide this, but conceptually the entry layer must not be one fragile box. DNS anycast, redundant appliances, or provider-managed control planes solve this. In an interview, you can state “the load-balancer tier is itself highly available” without designing its internal consensus.

### Common mistakes

- Treating round-robin as always optimal.
- Using sticky sessions to compensate for avoidable app-local state.
- Forgetting long-lived WebSocket draining during deployment.
- Assuming health checks should always test every downstream dependency.
- Saying “add a load balancer” when the real bottleneck is the database.


## Important interview ideas

> **Important:** A load balancer solves traffic distribution and instance failover. It does not fix an overloaded database, bad query, hot partition, or slow downstream dependency.

### Global vs regional balancing

A global system can use two levels:

```text
DNS / global traffic manager
        ↓
      Region
        ↓
regional load balancer
        ↓
application instances
```

The global layer chooses a healthy/nearby region. The regional layer chooses an instance. In most L4 interviews, you can draw this as one conceptual layer until multi-region becomes relevant.

### Health-check design

A health check should answer “can this instance serve traffic?” There are trade-offs:

- **liveness**: is the process alive?
- **readiness**: is it ready to receive traffic?
- **deep dependency check**: are critical dependencies usable?

If every instance marks itself unhealthy because one shared database is down, the load balancer may have nowhere to send traffic. So dependency failures sometimes require degraded behavior rather than ejecting all app servers.

### Load balancing and long-lived connections

For ordinary HTTP, requests can go to different servers. WebSockets are long-lived: once established, traffic stays on the owning gateway. During deployment, the server should stop accepting new connections, notify or wait for clients, and drain existing sockets.

### Consistent/hash affinity

Hashing on a key can route related requests to the same backend. This may improve cache locality or support stateful ownership. The downside is uneven load if keys are skewed. Hard affinity also makes failover harder.

## Routing strategy comparison

| Strategy | Good when | Main concern |
|---|---|---|
| round robin | requests similar | ignores duration/load |
| least connections | varied request duration | connection count may not equal work |
| weighted | servers/canaries differ | weights need tuning |
| hash/key affinity | locality/sticky ownership useful | hot keys/skew |

## Worked scenario — safe rolling deployment

Suppose 20 app instances serve HTTP and WebSockets.

1. Mark one instance **not ready** so no new connections arrive.
2. Continue serving existing requests/connections.
3. Drain or gracefully close WebSockets so clients reconnect elsewhere.
4. Stop the instance.
5. Deploy new version and pass readiness checks.
6. Return it to rotation.

Without draining, users see avoidable connection resets.

## Interview questions and model answers

### Q1. “Where should TLS terminate?”

Often at the L7 load balancer/API gateway for centralized certificate handling and routing. For sensitive internal networks, traffic can be re-encrypted to services. The choice depends on trust boundaries and operational needs.

### Q2. “Should health checks call the database?”

Sometimes readiness should reflect a critical dependency, but a deep check can eject all instances during a shared dependency outage. I distinguish liveness from readiness and design degraded behavior rather than treating every shared failure as an instance failure.

### Q3. “Do we need sticky sessions?”

Not for a properly stateless HTTP service. For persistent connections or explicit ownership, affinity can be useful, but correctness should survive reassignment after failure whenever possible.

### Q4. “Is the load balancer itself a single point of failure?”

Conceptually it must be highly available. Cloud-managed load balancers or redundant/anycast frontends hide this. In an interview I would state the LB tier is redundant rather than designing its internal consensus unless asked.

## Common mistakes to avoid

- Adding a load balancer before multiple backends exist with no reason.
- Thinking it increases database capacity.
- Using sticky sessions to hide poor state management.
- Forgetting health checks and draining.
- Ignoring long-lived connection behavior.
- Choosing hash routing without considering hot keys.

## Short revision note

Load balancing = **distribute traffic + remove unhealthy instances + support routing/deployment**. Always ask whether servers are stateless and what happens during draining/failure.

## Interview-ready synthesis

### A strong 60–90 second explanation

I introduce a load balancer when there are multiple interchangeable backends or when routing/health policy is needed. I state whether I need L4 transport routing or L7 HTTP-aware routing, define health/readiness behavior, and explain connection draining during deploys. For stateful sockets or locality, I discuss affinity only if it solves a real ownership problem.

### How this topic connects to the wider system

- Performance: routing algorithms influence utilization and hot-instance behavior.
- Reliability: health checks remove failed instances and draining avoids deployment errors.
- Scalability: multiple stateless instances can share traffic horizontally.
- Architecture: global routing and regional balancing can be separate conceptual layers.

### Revision flashcards with answers

**L4 vs L7?**  
L4 routes using transport information; L7 understands application protocol such as HTTP paths/headers.

**What is draining?**  
Stop new traffic while allowing in-flight requests/connections to finish before shutdown.

**Sticky sessions good or bad?**  
Useful for deliberate affinity/state, but reduce flexibility and make failover harder.

**Can LB fix a slow DB?**  
No. It only distributes traffic among backends; shared bottlenecks remain.

**What is readiness?**  
Whether an instance should currently receive new traffic, distinct from merely being alive.

### If the interviewer pushes deeper

Do not panic or jump to a named technology. Restate the new requirement, identify which assumption changed, and modify only the affected part of the design. A useful phrase is:

> “The original design optimized for ___. With this new requirement, the bottleneck/guarantee changes to ___, so I would introduce/change ___; the cost is ___.”

This is usually a stronger L4 signal than replacing the whole architecture.

## Cross-system connections

The value of this topic becomes clearer when you see it appear in different architectures:

- URL shortener: stateless redirect services can be horizontally balanced while mapping store/cache scale separately.
- Chat: long-lived sockets need connection-aware draining; a reconnect may land on a different gateway.
- Canary deployment: weighted L7 routing can send a small percentage of requests to a new version.

### When not to overuse this idea

Do not introduce sticky sessions for a stateless service just because a load balancer supports them. Affinity should solve a real state/locality requirement.

### A good interviewer sentence

> “I would use this only because the current requirement/workload creates the specific problem it solves. If that assumption changes, I would simplify or choose the alternative.”

This sentence captures an important L4 behavior: architecture is conditional, not dogmatic.
