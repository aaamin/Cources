# Lesson 05 — Load Balancing

**Phase:** Fundamentals  
**Session:** 5/46  
**Recommended time:** 60–90 minutes

## What you will learn

Learn why load balancers exist, L4 vs L7 behavior, routing strategies, health checks, draining, sticky sessions, and failure considerations.

This is **study documentation**. Read the explanations first; use the review section only after you have studied the lesson.

## Why load balance

Horizontal scaling creates multiple servers. A load balancer distributes requests and removes unhealthy instances from service. It improves capacity and availability, but the data layer and downstream dependencies must still scale.

## L4 vs L7

L4 balancing uses transport information such as IP/port and is protocol-agnostic. L7 understands application protocols such as HTTP and can route by path/header, terminate TLS, or enforce richer policy. Choose based on required routing intelligence.

## Algorithms

Round robin is simple; least-connections helps when request durations vary; weighted routing supports canaries or heterogeneous capacity; hashing can provide affinity but may create skew. No algorithm is universally best.

## Health checks

The balancer stops sending new work to unhealthy instances. Health checks should answer whether an instance can serve useful traffic. Overly deep checks tied to a shared dependency can accidentally remove every backend at once.

## Connection draining

During shutdown or deployment, an instance can stop accepting new work while finishing in-flight requests or long-lived connections. Draining reduces avoidable errors during rolling changes.

## Sticky sessions

Affinity sends the same client to the same backend. It can help legacy stateful apps but weakens load distribution and failover. Prefer stateless compute unless affinity is truly needed.

## Worked example — scaling a profile API

A profile API grows from one to ten stateless servers behind a load balancer. Health checks remove failed nodes; draining protects requests during deployments. If expensive image operations behave differently from normal API calls, L7 routing can direct them to a specialized pool.

## Interview lens

When adding a load balancer, say what it solves—horizontal scale, failover, routing—and whether backends are stateless.

## What to remember

Load balancers distribute traffic and participate in health/failover; they do not magically remove bottlenecks elsewhere.

## Deeper study notes

### Load balancing does not have to be one layer

A global system may have global traffic management that chooses a region, then a regional load balancer that chooses a service instance. Internal service-to-service traffic may also be balanced separately. In interviews, you can usually compress these into one or two conceptual layers unless regional routing is a focus.

### Health is not binary

A process can be alive but unable to serve useful traffic because its database pool is exhausted or it cannot load critical configuration. Conversely, if every instance fails a deep health check because one shared database is down, removing all instances gains nothing. Good health checks distinguish instance-local failure from shared dependency failure.

### Affinity can be deliberate

Sticky routing is not always bad. Stateful streaming sessions or caches may benefit from affinity. The question is whether correctness depends on it. If an instance dies, can the client reconnect elsewhere and restore state? If yes, affinity is an optimization rather than a hard dependency.

### Balancers themselves need redundancy

Managed/cloud load balancers hide this, but conceptually the entry layer must not be one fragile box. DNS anycast, redundant appliances, or provider-managed control planes solve this. In an interview, you can state “the load-balancer tier is itself highly available” without designing its internal consensus.

### Common mistakes

- Treating round-robin as always optimal.
- Using sticky sessions to compensate for avoidable app-local state.
- Forgetting long-lived WebSocket draining during deployment.
- Assuming health checks should always test every downstream dependency.
- Saying “add a load balancer” when the real bottleneck is the database.
